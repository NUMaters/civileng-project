# NPC ソロMVPの実装契約

2026-09-13。ユーザーの残りのMVP実装依頼を受け、ゲーム内の選択式会話に必要なローカルREST接続を実装した。型は `packages/game-schema/rest/npc.ts`、表示・知識データ型は `common/npc.ts` に集約する。

## 範囲と状態の管理

現在のソロゲームでは、準備・災害・結果の進行と浸水シミュレーションをブラウザが管理する。NPCサーバーは会話の所有トークン、ヒント段階、同時実行、重複要求、回答後の1秒制限を管理する。

このAPIはソロ用の接続契約であり、認証済みプレイヤーの所属やゲーム本体のフェーズを独立して検証するマルチプレイ用APIではない。`remainingSeconds` と準備中という状態はソロクライアントから受け取る。サーバーの既存ゲーム状態・Tickは未実装の箇所があるため、マルチプレイ統合時には権威あるゲームセッションへ接続し直す。`backend-interface.md` の将来のMain Backend / AI Backend間契約は引き続き別の設計対象。

既存のゲームWebSocketにNPC文章を流さず、質問したクライアントのHTTP応答だけに返す。LLM呼び出しはゲーム進行から独立する。

## エンドポイント

| 方法・パス                               | 入力                                                                   | 成功応答                                                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| POST /api/npc/conversations              | npcId, scenarioId, catalogVersion, phase=preparation, remainingSeconds | 201: conversationId, token, catalogVersion                                                                 |
| POST /api/npc/conversations/{id}/answers | requestId（UUID）, questionId, deeper                                  | 200: requestId, npcId, questionId, hintLevel, answerText, factIds, sourceIds, mode, fallbackReason（任意） |
| DELETE /api/npc/conversations/{id}       | 本文なし                                                               | 204                                                                                                        |

会話作成後は `Authorization: Bearer <token>` を使う。トークンをURL、ログ、localStorageへ保存しない。別の会話のトークンでは回答・終了できない。

最初の質問はレベル1。`deeper=true` は直前と同じ質問についてのみ許可し、サーバーが2、3へ進める。4以上には進めない。通常の質問選択は同じ質問であってもレベル1へ戻る。

不正JSON・未知のフィールド・未知の質問は400、所有トークン不一致・消失済み会話は401、不一致フェーズ・段階・重複・カタログ版は409、処理中・クールダウン・上限到達は429。これらの要求拒否を固定回答の成功に置き換えない。

JSON本文は2KBまで。Originがある場合は要求Hostとの一致を確認する。Viteの `/api/npc` プロキシは元のHostを保つ。公開運用時は同一オリジンのリバースプロキシ、適切な認証・レート制限が必要となる。

## 応答生成と根拠

`packages/game-data/npc/npc-catalog.json` をフロント・Goサーバー双方で読む。Goは既存の `GAME_DATA_DIR` 解決規則を使う。

質問・ヒントごとのFact IDから知識を直接取得する。各NPCには `topicFactIds` を持たせ、紹介以外の回答はそのNPCの担当Factだけを参照する。別NPCの質問ID、別の段階、未承認のFact、担当外のFactは生成対象にしない。検索型RAG、ベクトルDB、実行時Web検索は使用しない。

OllamaまたはOpenAIの構造化出力を使う。質問候補に対応付けた承認済みFactをサーバーが取得し、そのFact・人格・ヒント段階をLLMへ渡す。LLMは登録済みの言い回し候補から一つを選ぶだけで、知識の検索・追加・創作は行わない。受信後も候補との完全一致・120文字以内・2文以内・禁止パターンを検証する。

`factIds` と `sourceIds` は取得した知識からサーバーが付与し、LLMに作らせない。クライアントでも要求ID・質問・NPC・段階・登録済み本文・出典対応を検証する。一般住民のレベル3は人物設定に基づく紹介文のため、外部Fact IDなしの固定回答とする。

OllamaまたはOpenAIの失敗・タイムアウト・出力検証不合格・推論枠不足の場合、該当質問・段階の最初の登録回答を返す。API応答の `mode` は `ollama`、`openai` または `fixed`。`fallbackReason` は運用確認用で、ゲーム画面には表示しない。

## 終了・タイムアウト・同時実行

- Ollama生成は最大5秒、同時推論は4件まで。
- 同じ会話の同時質問は1件、受理済み要求IDの再利用は拒否。
- 回答後1秒は次の質問を拒否。
- 会話は作成時点の準備残り時間で失効する。期限切れの結果は確定しない。
- 閉じる・NPC切替・フェーズ変更・メニュー復帰で、クライアントは要求を中止し、会話をDELETEする。
- サーバーはDELETEまたはHTTP切断時に生成を中止し、遅い応答を確定しない。
- クライアントも会話世代と最新フェーズを再確認してから表示する。
- 最大256会話、1会話64要求。期限切れはアクセス時に回収する。
- 会話はメモリ内のみ。本文やプロンプトはアプリケーションの運用ログに保存しない。

Goサーバーがない場合や通信に失敗した場合も、クライアントに同梱した同じ知識・回答・出典で会話を続けられる。通信失敗後はその会話全体を固定回答へ切り替え、サーバーとヒント段階がずれることを避ける。要求拒否の場合は会話を開き直す案内を出す。

## 災害と結果画面

災害中はOllamaを使わない。NPCから設定半径内の `overflowSites` を参照し、最も強い越水・侵食・内水・流下能力不足の表示を定型文へ対応付ける。これはゲーム内の被害発生点の近傍判定であり、NPC足元の水深の推定ではない。

住宅・道路ごとの被害状態は現在のゲーム状態にないため、個別の被害を創作しない。現実の一般的な防災情報は別の文として表示する。

結果画面には、そのプレイで実際に表示した回答・防災情報のFact IDに結び付く資料だけを重複除去して表示する。質問の取り消し、生成待ちのままの終了、NPCを開いただけの準備中会話は、出典利用として数えない。
